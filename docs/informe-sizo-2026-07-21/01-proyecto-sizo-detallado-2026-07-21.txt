1. QUÉ ES SIZO
================================================================

al mercado colombiano. Es un producto propio de Webcore Solutions (no es
un desarrollo para un cliente externo, sino un producto que la empresa
comercializa).

3. ARQUITECTURA TÉCNICA
================================================================
Stack:
- Frontend: HTML/CSS/JavaScript vanilla — SPA sin framework, con
  módulos ES (ES modules). Sin React/Vue/Angular.
- Autenticación: Supabase Auth, JWT con app_metadata que contiene
  tenant_id, role y empresas_ids.
- Base de datos: Supabase PostgreSQL con Row Level Security (RLS)
  multitenant.
- Storage: Supabase Storage, bucket "documentos" (PDFs firmados).
- Manipulación de PDF en cliente: pdf-lib (UMD) + signature-pad (UMD),
  vendorizados en la carpeta vendor/.
- Despliegue: GitHub Pages. Push a main despliega automáticamente.

Decisiones de arquitectura clave:
- SPA basada en hash: router.js carga módulos ES dinámicamente según
  window.location.hash. El evento hashchange maneja la navegación
  normal; popstate maneja el botón "Atrás" del navegador (en
  particular el regreso al dashboard consolidado).
- Store reactivo propio (store.js): funciones get/set/subscribe sin
  dependencias externas. Los módulos se suscriben a "empresa" y
  "periodo" para re-renderizarse cuando cambian.
- Multitenancy real vía RLS: toda la seguridad efectiva vive en
  Supabase (políticas RLS). El "gating" de rutas en el router es solo
  para UX, no es una barrera de seguridad real.
  Helpers RLS definidos en 001_schema_inicial.sql:
    tenant_id(), is_admin(), user_role(), can_read_empresa(),
    can_write_empresa()
  Regla importante: usar (select tenant_id()) y no tenant_id()
  directo, para evitar que la función se evalúe fila por fila
  (optimización InitPlan, ver hallazgo H10).
- Creación de usuarios: se hace vía Edge Function
  (supabase/functions/crear-usuario/index.ts) porque requiere
  privilegios service_role para escribir app_metadata, algo que no
  se puede hacer desde el cliente.
- Vendor: librerías de terceros como archivos UMD sueltos en vendor/,
  que se publican junto con el resto del sitio. Se cargan con
  new URL('../vendor/archivo.js', import.meta.url).href para que
  funcione bajo el path base /SiZO/ de GitHub Pages.
- Migraciones: se aplican manualmente en el SQL Editor del Supabase
  Dashboard. No existe un psql local ni credenciales de base de datos
  directas configuradas.

4. MODELO DE ROLES
================================================================
- ADMIN: acceso total a todas las empresas del tenant.
- ASESOR: solo puede ver/escribir las empresas que tiene asignadas
  (según empresas_ids en el JWT).
- CONSULTA: solo lectura de sus empresas asignadas, no puede crear,
  editar ni eliminar.

5. MÓDULOS EN PRODUCCIÓN (detalle técnico)
================================================================
Ver documento complementario "02-que-tiene-sizo" para el listado
funcional. A nivel técnico, algunos módulos tienen lógica separada
en motores puros sin DOM, para facilitar testing:
- calcular-riesgo-gtc45.js: motor de cálculo de la Matriz de Riesgos.
  Fórmula: ND × NE = Probabilidad; Probabilidad × NC = Nivel de
  Riesgo → se traduce en zona (I a IV) y aceptabilidad. Los niveles
  se calculan una sola vez al guardar (antesDeGuardar) y se persisten
  ya resueltos, no se recalculan en vivo dentro del modal.
- calcular-indicadores.js: motor de indicadores SG-SST. HHT
  (Horas Hombre Trabajadas) = trabajadores × días trabajados × 8.
  Para IFA/IFM/ISA se usa la escala 240.000 según Decreto 1072 Art.
  2.2.4.1.7. Para "incidenciaEl" se usa la escala 100.000 según
  Resolución 0312/2019 — son dos escalas distintas que no deben
  confundirse.

Componente compartido:
- components/exportar-plantilla.js: centraliza exportación a Excel
  (SheetJS) y PDF (jsPDF + autoTable) para cualquier módulo tabular.
  Expone botonesDescarga({ tabla, titulo, columnas, nombreBase,
  urlOficial }), que genera botones "Excel" y "PDF" (releen la tabla
  en cada click, no dependen del estado interno del CRUD), y
  opcionalmente un botón "Formato oficial" que enlaza a la fuente
  pública (ARL o universidad) del formato en blanco. No se
  redistribuye la GTC 45 de ICONTEC (es de pago), sino recreaciones
  libres equivalentes. Está cableado en: matriz-riesgos, matriz-epp,
  entrega-epp, actas, casos y auditoria. El Gestor Documental NO usa
  este componente porque es la vista completa del repositorio, no un
  listado exportable.
  Cuidado técnico: el "titulo" pasado a exportarExcel se usa como
  nombre de hoja de cálculo; Excel prohíbe los caracteres
  : \ / ? * [ ] — ya están saneados dentro de la función, pero hay
  que evitarlos si se llama fuera de botonesDescarga.

      usuarios_proteger_columnas.

      mensaje genérico.
H6  — supabase-js se cargaba desde CDN → vendorizado en
      vendor/supabase-js@2.108.1.js.
H7  — Sin Content-Security-Policy → se agregó <meta> CSP en
      index.html. Los headers HTTP en Cloudflare siguen pendientes.
H8  — Queries sin límite → db.js list() aplica .limit(500) por
      defecto.
H9  — El JWT no se refrescaba al volver al foco de la pestaña →
      listener de visibilitychange que llama a refreshSession() en
      auth.js.
H10 — Políticas RLS sin InitPlan (se evaluaban fila por fila) →
      se envolvieron las funciones en (select fn()) en todas las
      políticas.
H11 — El motor de indicadores estaba mezclado con lógica de DOM →
      se extrajo a calcular-indicadores.js, puro.
H12 — Cálculo de HHT incorrecto en IFA/IFM/ISA → corregido a base
      240.000 según Decreto 1072.
H13 — No existía recuperación de contraseña → se agregaron
      #forgot-form / #reset-form y manejo del evento
      PASSWORD_RECOVERY.
H14 — El store tenía una variable desactualizada (_empresas) →
      corregida y comentarios actualizados.
H15 — Los nombres de los asesores no se resolvían en pantalla →
      empresas.js ahora carga usuarios en paralelo para resolverlos.

7. BUG DE RLS EN DOCUMENTOS (2026-07-16) — SIN EXPLICACIÓN RAÍZ
================================================================
El soft-delete (poner activo=false) en la tabla "documentos" era
rechazado con el error 42501 ("new row violates row-level security
policy") para un usuario ADMIN, a pesar de que la política de RLS
era, tras verificación exhaustiva, correcta.

Se descartaron como causa, uno por uno:
- Tabla duplicada
- Trigger personalizado
- Revisión de pg_rules
- Llave foránea autorreferenciada (raiz_id / version_anterior_id)
- Triggers internos de llave foránea
  (probado con session_replication_role=replica)
- Interacción con la cláusula RETURNING
- Caché de plan genérico (se probó envolver con
  (select fn()) igual que en H10)

Prueba definitiva de que no era un problema de la condición lógica:
dentro de la MISMA transacción y con el MISMO rol, un SELECT que
evaluaba exactamente la expresión del WITH CHECK justo antes del
UPDATE fallido devolvía true — y aun así el UPDATE era rechazado.

Se intentaron tres migraciones sucesivas antes de llegar al
workaround definitivo:
- 009_fix_documentos_rls.sql (WITH CHECK explícito) — no resolvió.
- 010_simplificar_rls_documentos.sql (quitar subquery innecesaria
  en can_write_empresa) — no resolvió, no llegó a aplicarse porque
  se saltó directo al intento 3.
- 011_fix_cache_rls_documentos.sql (mismo patrón InitPlan de H10)
  — tampoco resolvió.

Workaround aplicado y vigente (012_rpc_soft_delete_documento.sql):
una función soft_delete_documento(uuid) con SECURITY DEFINER que
valida los permisos en PL/pgSQL manualmente y ejecuta el UPDATE como
dueño de la tabla, evitando por completo el camino de RLS que fallaba
sin explicación. El módulo gestor-documental.js llama a esta función
vía supabase.rpc('soft_delete_documento', ...) en lugar de usar
db.softDelete.

Nota para el futuro: si el mismo síntoma aparece en otra tabla
(por ejemplo, soft-delete de matriz_riesgos o actas vía _crud.js /
db.softDelete), la recomendación es replicar directamente el mismo
patrón de función RPC en lugar de seguir depurando la política RLS,
porque ya se agotó el espacio razonable de diagnóstico por SQL
directo.
